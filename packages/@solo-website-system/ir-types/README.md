# @solo-website-system/ir-types

TypeScript declarations and JSON Schemas (Draft 2020-12) for the Solo Website System (SWS) intermediate representation. License: `MIT OR Apache-2.0`.

The package ships **declarations and JSON only**: no JavaScript, no runtime, no dependencies.

## What is generated

Everything except this README is generated from the Rust types in `crates/sws-ir`. Do not edit it by hand.

| File | Source |
| --- | --- |
| `index.d.ts` | Rendered from the schemas below (`SiteDocument`, `Node`, `Page`, `IrPatch`, `CommandBatch`, `Command`, `Transaction`, `UpgradeReport`, `CommandError`, and every type they reference). |
| `schema/site-document.schema.json` | `sws_ir::SiteDocument` (`$id` `https://solo-website-system.example/schemas/site-document.v1.json`, unchanged from the earlier hand-written schema). |
| `schema/ir-patch.schema.json` | `sws_ir::IrPatch`, the declarative patch operations (`$id` `https://solo-website-system.example/schemas/ir-patch.v1.json`). |
| `schema/command-batch.schema.json` | `sws_ir::edit::CommandBatch`, the versioned editor command batch and every `Command` / `ContainerRef` (`$id` `https://solo-website-system.example/schemas/command-batch.v1.json`). |
| `schema/transaction.schema.json` | `sws_ir::edit::Transaction`: `version`, `forward`, `inverse` (both command lists) and `touched` field paths (`.../transaction.v1.json`). |
| `schema/upgrade-report.schema.json` | `sws_ir::edit::UpgradeReport`, the result of the explicit stable-ID upgrade (`.../upgrade-report.v1.json`). |
| `schema/command-error.schema.json` | `sws_ir::edit::CommandError`: `code` (an `ErrorCode`), `message`, optional `command_index`, `paths` (`.../command-error.v1.json`). |
| `package.json` | Template in `crates/sws-codegen`; the version follows the workspace version. |

The hospitality pack schema `packs/hospitality/schema/venue.schema.json` is generated by the same command from `VenueManifest` in `packs/hospitality/crate`. It stays in the pack, not in this package.

Generation runs entirely in Rust (`schemars` derives behind the `jsonschema` cargo feature, which is never enabled for the Wasm or Worker builds). Node is not involved.

## Regenerate

```sh
npm run codegen         # rewrite the generated files
npm run codegen:check   # fail if they differ from the Rust types (also part of `npm run verify`)
```

After changing a type in `crates/sws-ir` (or `VenueManifest`), run `npm run codegen` and commit the result together with the Rust change.

To add a root type, derive `JsonSchema` on it (behind `feature = "jsonschema"`) and add one line to `core_roots()` in `crates/sws-codegen/src/lib.rs`. Its fields, nested types and `.d.ts` declarations follow automatically.

## How the schema maps serde

- Internally tagged unions (`Node` tag `type`, `RoutePattern` tag `kind`, `IrPatch` tag `op`) are `oneOf` branches with the tag as a `const`.
- `#[serde(default)]` fields are not `required`. In the `.d.ts` they are optional properties.
- IR optionals serialize as `null`, so they are `T | null` (`T | null | undefined` for authoring input).
- `BTreeMap<String, T>` is `additionalProperties` / `Record<string, T>`. Free-form `serde_json::Value` is unconstrained (`unknown`).
- Enums such as `PropKind` and `FormFieldKind` are snake_case string unions.

One TypeScript type is generated per Rust type. It describes what a tool may write. A document serialized by `solo` includes every key except those the Rust types omit when empty: `uid` is omitted when it is `None`, and `CommandError.command_index` and `paths` are omitted when unset. Optional fields that are written serialize as `null`.

## Editor contract (`uid` and command batches)

The editor reducer (`sws_ir::edit`, contract in `docs/EDITOR_COMMANDS.md`) is part of the generated surface, so Studio, MCP and other tools get its wire format from the Rust types instead of a hand-kept copy.

- **`uid`.** Every `Node` variant has an optional `uid` (never rendered). The schema gives it the pattern `^[a-z0-9][a-z0-9._-]{0,63}$` (uniqueness across the document is not expressible in JSON Schema; `check_editable` enforces it). The same pattern applies to every `uid` that a command, container reference or `UpgradeReport` entry carries. `"uid": null` is accepted, as the parser accepts it; the writer never emits it.
- **Upgrade marker.** An upgraded document has `metadata["sws.ir"] = {"uid_scheme": 1}`. `metadata` stays free-form, so the schema does not check the marker; `check_editable` does.
- **Batch.** `CommandBatch.version` is the literal `1` (`COMMAND_BATCH_VERSION`, independent of `schema_version`), and `commands` has 1 to 1000 entries (`empty_batch`, `batch_too_large`). `Transaction.version` is `1` as well.
- **Commands.** `Command` is a `oneOf` tagged by `op` (snake_case, 22 ops); `ContainerRef` is tagged by `kind` (`page_body`, `component_template`, `node`). Both reject unknown fields, as do embedded `node`, `page` and style `rule` payloads (the strict parser does the same). Optional fields may be omitted or `null`.
- **Errors.** `CommandError.code` is the closed `ErrorCode` enum (20 snake_case codes), with `message`, optional `command_index` and `paths`.
- **Not in the schema.** Relations between values, such as which `slot` suits which node kind or whether a `uid` exists, are reducer checks (`invalid_container`, `not_found`, ...), not schema checks.

## Constraints are kept in the schema

The original hand-written schema carried value constraints that plain derives do not produce. They are restored with `schemars` attributes next to each field in `crates/sws-ir/src/types.rs`, schema only: no parser or `validate_ir` behaviour changed. They are: `schema_version >= 1`, the `slug` pattern, the `https` `base_url` pattern and `format: uri`, `minItems: 1` and `required` for `pages`, `#rrggbb` color values, `minLength: 1` on names, ids, selectors, tags, expressions and `src`, `exclusiveMinimum: 0` for `min_ratio`, `max_chars >= 0`, `^/` for route paths and patterns, and `required` plus `minItems: 1` for dynamic route `params`.

`crates/sws-codegen/tests/ir_schema.rs` freezes the old schema (`tests/fixtures/site-document.schema.legacy.json`) and proves the generated one is not looser: every old constraint is present, and both schemas accept and reject the same documents over targeted edits and thousands of structural mutations. The only deliberate differences are `uid` and the `u32` upper bound on `schema_version` (4294967295), which serde enforces and the old schema did not state; integer widths of 32 bits or fewer are emitted as `minimum`/`maximum`, while 64-bit and `usize` fields keep only the type and lower bound (their bounds are not exactly representable as JSON numbers). `crates/sws-codegen/tests/editor_contract.rs` checks the schemas against values produced by the real reducer.

## Venue manifest caveat

`packs/hospitality/schema/venue.schema.json` (also generated) is inherited from the hand-written schema and marks two keys `required` that the Rust serializer omits when empty: `modules` (omitted when the map is empty, `skip_serializing_if = "BTreeMap::is_empty"`) and `scheduling.events.google_calendar_id` (omitted when `None`). So a manifest serialized from Rust with no modules, or with no calendar id, does not validate against the schema, while hand-written JSON that includes the keys (the demo fixture, `"google_calendar_id": null`) does. This is pinned by a test so a future change is deliberate; neither the serialization nor the schema was changed.

## Unknown-field policy

The schema is **strict** and the Rust parser is **tolerant**, on purpose.

- Every struct-like object has `additionalProperties: false`, so authoring tools and editors reject typos and unknown keys.
- The Rust IR parser has no `deny_unknown_fields`: `solo build` and `solo check` ignore unknown keys, so existing files keep building. The editor command types (`CommandBatch`, `Command`, `ContainerRef`) do deny them, and the schema matches. Unknown enum tags (for example a `Node` `type` or a `RoutePattern` `kind`) are errors in both.
- Free-form maps (`data`, `metadata`, component `props`, JSON-LD `data`) stay open.

A document that the schema rejects may therefore still build. Do not treat schema validity as a build gate.

## Also validate with `validate_ir`

JSON Schema cannot express document-wide rules. A schema-valid document can still fail `sws_ir::validate_ir`: page ids and routes must be unique, routes are canonicalised, `base_url` must be https, slugs must match their grammar, `schema_version` must be 1, and so on. Run `validate_ir` (`solo check`) as well as the schema.
