# Studio site command sessions

`MIT OR Apache-2.0`

Implemented by issue #62 in `crates/sws-worker-studio/src/session/`. One SQLite-backed, hibernating Durable Object (`SiteSession`, binding `SITE_SESSION`) per site owns the live document. Command reduction is always the Rust reducer in `sws_ir::edit` ([`EDITOR_COMMANDS.md`](EDITOR_COMMANDS.md)); sessions never reimplement it. Pure logic (protocol, engine, rebase rules, authorization policy, attachments, SQL) is host-tested; only the Durable Object, DO SQL adapter and Worker entry are wasm-only.

## Route and identity

`GET /api/sites/{workspace_id}/{site_id}/session` with `Upgrade: websocket`. Order: request bounds, **browser Origin gate** (`403 forbidden_origin`: a request that carries an `Origin` must equal `STUDIO_PUBLIC_ORIGIN` after normalisation (scheme and host are case-insensitive, a default port `:443`/`:80` and a trailing `/` are ignored; a different port, a path, `null`, an empty value or a host suffix never match), checked before authentication so cross-site WebSocket hijacking never reaches cookie credentials (#65); requests with no `Origin`, i.e. CLI and MCP token clients, are allowed; an unset `STUDIO_PUBLIC_ORIGIN` refuses browser origins), authenticate (`401 unauthenticated`), membership in D1 (`403 forbidden`, also for an unknown workspace), site exists in that workspace (`404`), then the request is forwarded to the object named `workspace_id/site_id` (ids are `[a-z0-9_-]{1,64}`, so names cannot collide). A plain GET answers `426`. Until #65 ships, `auth::authenticate` rejects everyone; only the local test build (`--features insecure-dev-auth`, never part of `build/` or any deploy, guarded by `npm run check:studio:release`) accepts `X-Sws-Dev-User`.

## Messages

One JSON text frame each, `{"v":1,"type":...}`, parsed strictly (unknown fields, versions or types are errors; nothing panics on input). Client: `ping`, `sync{since_seq?}`, `seed{document}`, `batch{op_id,base_seq,batch}`, `undo{op_id,target_seq}`, `checkpoint{reason: save|publish}`, `presence{state}`, `presence_get`. Server: `welcome`, `pong`, `state`, `replay`, `ack`, `entry`, `presence`, `checkpoint`, `conflict`, `error`, `revoked`. `batch` carries an ordinary command batch, parsed by `sws_ir::edit::parse_batch`. Every applied command is an `entry` with the next `seq`, delivered to all other sockets in log order; the sender gets an `ack`.

**Ordering guarantee.** The object handles inbound messages one at a time through a FIFO (a ticket is taken the moment a message arrives; the handler runs when every earlier message has finished), although handlers await D1. So messages are applied in the order they arrived: per socket, a client may pipeline `batch` N+1 (based on `base_seq` N) before the `ack` of N and both apply in send order, and replies (`ack`, `pong`, ...) come back in that order; across sockets, arrival order at the object decides. The guarantee is per object, not global: separate sites are independent. The FIFO is bounded: with 32 messages already held or waiting, a further message is answered `error` `rate_limited` and is not queued, so a flooding socket cannot grow memory (the accepted ones still apply in order; the client resends the refused ones). The FIFO covers messages only: the alarm and `/internal/revoke` deliberately do not wait in line (revocation must be immediate), which is why every handler re-reads the socket's attachment after each await (see below).

## Rules

- **Idempotency.** An `op_id` (8-64 chars) is remembered for 24 h (at most 5000) together with a hash of the request it produced (kind and content). A retry of the same request returns the original `seq` with `duplicate: true` and changes and broadcasts nothing, even if the document has moved on. Another user reusing the id, or the same user reusing it for a different batch or an undo, is refused with `op_id_reused` (never a silent duplicate ack for something that was not applied).
- **Stale batches** (`base_seq` behind the head). Rebased onto the head only when every command is an explicit independent field update (`set_site_meta`, `set_color_token`, `set_font_token`, `set_data_value`, `set_attr`, `set_text`, `set_tag`, `set_classes`, `set_style_refs`) and none of its touched fields overlaps one touched by an entry after `base_seq`. Otherwise a `conflict`: `stale_structural` (insert/remove/move/page/rule structure, token or data removal, even without overlap), `field_conflict`, `target_changed`, or `base_too_old` (older than the retained log; `sync`). Each names the head, the conflicting `seqs` and `paths`, and says what to resend.
- **Undo** is a new log entry applying the target's recorded inverse. Own entries only (`undo_not_owner`); `undo_incompatible` if any later entry touched an overlapping field, including a later undo of the same entry; `undo_too_old` after compaction. Undoing an undo is a redo. History is never rewound.
- **Presence** is a bounded JSON object (512 bytes), one per socket, expiring after a TTL (default 30 s), rate limited, removed on disconnect, pruned by the alarm.

## Persistence and checkpoints

DO SQLite holds the latest snapshot, the command log (contiguous `seq`, immutable rows, enforced by triggers), the operation index and presence. Waking from hibernation rebuilds from the snapshot plus a replay of the log tail. D1 is written **only** at a checkpoint: every 50 commands, or on `checkpoint` save (any member) / publish (publisher or owner). A checkpoint writes the snapshot locally and queues exactly one `site_revisions` row (id derived from workspace, site, seq and hash; `ON CONFLICT (id) DO NOTHING`, so retries are safe). The pending row survives eviction; transient failures (an outage, a timeout) retry from the alarm with backoff (2 s doubling, 5 min cap), and edits are refused (`checkpoint_backlog`) if 200 commands pile up unsaved. A **constraint** failure can never succeed on retry, so it is classified permanent: the checkpoint is re-attributed to the workspace owner (for example when the recorded author no longer exists) and written; if that is impossible too, the pending row is dropped with a logged `ALERT` and a `checkpoint` message with status `abandoned`, so edits resume instead of wedging the site. The next automatic attempt comes `CHECKPOINT_EVERY` commands after the dropped one (never per edit), and an explicit save can always take a fresh checkpoint. The alarm also compacts the log to the 50 entries below the latest snapshot (idempotent, forward-only), prunes expired operation ids and presence, and runs the membership sweep.

### Storage atomicity

Every engine call runs inside `ctx.storage.transactionSync(..)` (workers-rs 0.9 does not wrap that API, so the object calls it through JS), so the several DO SQL statements of one command (log row plus operation id; snapshot plus meta; compaction) commit together or roll back together. The outcome is decided from facts, never from a leftover flag: the store failure flag is cleared at the top of each transaction (a failed read made earlier cannot roll back, or falsely fail, a later write), a `transactionSync` that itself throws counts as failure even when no statement failed, and on any failure the cached engine is dropped (so the next message rebuilds from durable state; memory is never trusted after a rollback) and the call returns an error, never the closure's result, so a client is never acknowledged for work the transaction discarded. The engine also adopts new `Meta` only after `save_meta` succeeded. The client sees `unavailable` and may retry with the same `op_id`, which then applies exactly once. If a runtime lacks `transactionSync` the object **fails closed**: it runs no engine call at all (every message answers `unavailable`) rather than write non-atomically. The DO SQL schema is created on first use; the `ops.payload` column added after the first #62 commit is added to older state by a guarded `ALTER TABLE` (a "duplicate column" error means already applied), and `GET /internal/revision` on an object that never held a session answers `404` without creating any table. The local test proves `transactionSync` exists in workerd and rolls back (`POST /api/dev/tx-probe/...`).

### Checkpoint revisions and the contract #64 consumes

A checkpoint's `revision_id` (`ck-` + 24 hex) is the D1 `site_revisions.id`, announced in the `checkpoint` message (`pending`, `written`, `abandoned`, or `unchanged`). `unchanged` carries the id of the last checkpoint (a publish of an unchanged site publishes that revision and pins it). The object retains the snapshot bytes for the pending checkpoint, the latest confirmed checkpoint (`meta.last_revision`) and the latest confirmed **publish** checkpoint (at most three stored snapshots; the prune keeps exactly `seq` = latest, the confirmed checkpoint and the confirmed publish), keyed by `revision_id`, so the last confirmed revision stays fetchable while a newer one is stuck pending behind a D1 outage; older revisions are not held here (the previous confirmed one is pruned when the next checkpoint is taken). #64 reads them through `session::entry::fetch_revision(env, workspace_id, site_id, revision_id)` (internal `GET /internal/revision?id=...` on the site object), which returns `{revision_id, seq, sha256, document}` (the canonical IR JSON, whose SHA-256 equals the D1 row's `ir_sha256`) or `None` once that revision is no longer retained; #64 must therefore read a publish revision right after it is written, or rely on it being the latest publish.

## Bounds

Message 1 MiB (256 KiB except `seed`), document 1 MiB canonical JSON, 200 commands per batch, 16 sockets per site (4 per user), 512-byte presence, `base_seq`/`target_seq` validated. `seed` needs publisher or owner, only on an empty site, and is gated like `solo edit` (editable, lossless).

## Authorization after hibernation

The socket attachment (`client_id`, `user_id`, last verified role, `credential` reserved for #65) is restored after hibernation, but it is identity, not authority. The role is re-read from D1 before every state-changing message (so a removed or demoted member can never apply an edit), before a read when the cached verification is older than `SESSION_AUTHZ_RECHECK_MS` (default 15 s, hard cap 30 s), and for every other socket before any broadcast that a message triggers (batch, undo, seed, checkpoint, presence). A removed member receives `revoked`, a 4403 close, and no further entries.

**Revocation is sticky.** Every handler awaits D1 (`recheck`, `recheck_peers`, the checkpoint flush). After each await the socket's attachment is read again and the membership result is merged onto that fresh copy (`attach::merge_membership`); a pre-await copy is never written back, so a revocation (`/internal/revoke`, another recheck) that landed meanwhile cannot be reset to `revoked: false`. Immediately before the synchronous commit (`submit_batch`, `submit_undo`, `seed`, `take_checkpoint`) the socket is checked once more, and a revoked socket's message is dropped without applying or broadcasting anything.

**Delivery gate and wake cadence.** Delivery is synchronous (ordering), so it cannot await D1. Instead every send checks the age of the target's last verification and skips any socket whose verification is two recheck intervals old (`authz::delivery_allowed`). The gate depends only on the stored `authz_checked_ms`, so it holds after hibernation and regardless of when the object next wakes: **a removed member is sent nothing more than `2 x SESSION_AUTHZ_RECHECK_MS` after their last successful verification, at most 30 s by default and 60 s at the cap**, even if D1 stays unavailable (the checks fail closed; sockets are kept open and recovered later). The alarm no longer ticks every recheck interval: while sockets are attached it fires on `SESSION_IDLE_SWEEP_MS` (default **60 s**, clamped to `max(1 s, SESSION_AUTHZ_RECHECK_MS)` .. **60 s**, so the sweep can never cost more D1 reads than the recheck interval allows), plus the real work alarms (checkpoint retry, compaction, presence and operation-id expiry). That sweep only closes sockets of removed members that are otherwise idle and keeps the object able to hibernate between ticks; the old 15 s tick kept it awake. There are two bounds. **Delivery** to a removed member stops within `2 x SESSION_AUTHZ_RECHECK_MS` of their last verification (30 s default, 60 s at the cap). **Closing** an idle removed member's socket takes at most `SESSION_IDLE_SWEEP_MS` (60 s at most, the #60 decision) plus one D1 read; delivery has already stopped by then. If the engine cannot be opened when the alarm is re-armed, the idle sweep is still armed while sockets are attached (a removed member's socket is never left without a sweep).

**First message after a wake-up.** After eviction nothing is cached in memory, and the first message may be a write or a read with a stale authorization cache. The membership recheck resolves the workspace from DO storage (opening the engine), so it works as the very first thing the new instance does; the local test proves a `batch` and a stale-cache `sync` as the first messages after a verified eviction. Between the role check and the commit the socket's attachment is re-read once more and the action re-authorized against it (a peer's recheck may have demoted the member during an await), so a demoted publisher's publish is refused. A `presence` message queued behind a close is dropped (a closed socket's row is not resurrected).

**`ping` and D1 outages.** `ping` is a read: when the cached verification is older than `SESSION_AUTHZ_RECHECK_MS` it re-reads membership first, so during a D1 outage with a stale cache it answers `unavailable` instead of `pong` (an unverified socket gets nothing, also for liveness checks). Clients should treat `unavailable` as retry-later, not as a dead connection.

**Hooks for #65.** The 60 s bound of the #60 decision holds for delivery as shipped. What #65 must add: (1) in `object::fetch_role`, also validate the session or token behind `att.credential` (D1 session/token row not expired or revoked), so credential expiry joins the same recheck and gate; (2) call `session::entry::revoke_user(env, workspace_id, site_id, user_id)` (internal `POST /internal/revoke`) from logout, token revocation and membership change, for an immediate close instead of waiting for the gate; (3) make `entry::open` set `X-Sws-Internal-Credential` (the Worker always overwrites the internal headers); (4) its own measured test (the local test already drives `revoke_user` and the gate through dev-only routes).

## Local tests and what they prove

`npm run test:studio:sessions` builds the Worker with `insecure-dev-auth` into `crates/sws-worker-studio/build-dev-auth`, runs `wrangler dev -c wrangler.studio-sessions.jsonc` on port 8790 with its own persisted state, and drives real WebSockets. The dev-auth build is fenced at runtime as well as compile time: it answers `401` unless the `Host` is loopback **and** the var `SWS_INSECURE_DEV_AUTH=1` is present, which only the script passes (`--var`; no committed config sets it, and `wrangler.studio-sessions.jsonc` sets `workers_dev: false`; `npm run check:studio:release` asserts both). Only that build serves the test-only `/api/dev/...` routes (`entry::revoke_user`, `entry::fetch_revision`, a `transactionSync` probe, and a simulated D1 outage). It proves multi-client ordered sync, pipelined messages applied in send order, idempotent retries (and refusal of a reused id), rebase/conflict rules, undo, presence expiry, exactly one D1 revision row per checkpoint, the Origin gate, connection caps (429), membership removal and `revoke_user` (including an edit racing the revocation), fail-closed behaviour with D1 unavailable, the DO-level `checkpoint_backlog` and its recovery, re-attribution of a checkpoint whose author was really deleted (D1's own `FOREIGN KEY constraint failed`) or dropping of an unwritable one, the `rate_limited` FIFO cap, retained revision bytes, `transactionSync` rollback, state surviving a full process restart, and hibernation: the object is evicted while the socket stays open and a new instance (different `instance_id`) serves the first message after the wake-up (a batch; on a second site a sync with a stale authorization cache) from the restored attachment and DO SQL, with eviction verified afterwards by a ping rather than by one that opens the engine first. It does **not** prove production eviction timing, billing or duration behaviour, multi-region placement, or behaviour across deploys (a deploy disconnects sockets; clients must reconnect and `sync`). Real latency and quotas remain assumptions until verified on a Free account (#59, #69).
